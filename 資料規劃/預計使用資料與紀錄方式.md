# 預計使用資料與紀錄方式

更新日期：2026-11-13（Asia/Taipei）

操作、檔案用途、資料更新與備份還原方式，見 [維護方式](./維護方式.md)。

本文件記錄我們預計使用哪些資料、多久取得一次、怎麼保存，以及缺漏時怎麼處理。**目前是規劃，資料收集後端尚未建立，也尚未將這套來源接到網站。** 所有日期與時間均採臺灣時間。

## 目前預計使用的資料

主要提供「現在、過去一週、未來一週」的溫度、體感、濕度，以及每日最高／最低氣溫與體感。

| 用途 | 預計使用的資料 | 來源 |
| --- | --- | --- |
| 現在 | 氣溫、體感、相對濕度 | 最新鄉鎮 GT，使用同鄉鎮、同資料時間的一組數值 |
| 過去一週走勢 | 每小時的氣溫、體感、相對濕度 | 官方鄉鎮過去 24 小時資料，持續保存並逐步累積一週 |
| 今天已取得的紀錄及過去日期高低值 | 氣溫、體感各自的最高與最低紀錄 | 持續比較最新 GT，並納入補回的有效整點資料 |
| 未來近期走勢 | 氣溫、體感、相對濕度 | 官方整包 F-D0047-093 的短期預報 |
| 未來較遠走勢 | 平均氣溫、平均相對濕度，以及最高／最低氣溫與體感 | 整包內的日夜／逐 12 小時預報 |
| 每日預報高低值 | 最高／最低氣溫與體感 | 整包內的逐日預報，保留每筆實際涵蓋時間 |

過去及現在的體感直接使用官方 GT 數值，不自行套公式補成官方體感。較遠預報只有體感高低值時，以範圍呈現，不把高低平均值當成官方單一體感。

## 預計多久取得一次

| 對象 | 預計取得與處理方式 | API key |
| --- | --- | --- |
| 最新 GT | 每 **10 分鐘**檢查；取得新資料才更新現在畫面，並比較當日高低紀錄 | 不需要 |
| 鄉鎮過去 24 小時 | 每 **1 小時**重讀，與已保存的整點資料比對，補入新資料、缺漏及已確認的修訂 | 不需要 |
| 超過 24 小時至過去一週 | 讀取我們已保存的整點資料；隨每小時補齊作業更新 | 不需要 |
| 未來整包 F-D0047-093 | 每 **1 小時**檢查，有新版才更新對應預報 | 需要 |

上述是我們預計的檢查頻率，尚未實作；不代表官方每次都有新值，也不代表 GT 固定每 10 分鐘發布。官方預報發布時間與本次實際資料間隔，詳見來源文件。

預計由後端集中取得、保存，供所有使用者共用，關閉前端網頁後仍持續執行。整包所需 API key 由後端保管；目前本機測試使用根目錄 `.env` 的 `CWA_API_KEY`，不寫入文件或版本控制。

## 走勢的時間怎麼保留

| 範圍 | 預計使用方式 |
| --- | --- |
| 現在 | 保留 GT 原始資料時間，可能不是整點；畫面同時讓使用者知道資料時間 |
| 過去一週 | 使用官方過去 24 小時來源的整點值，每小時一筆，逐步累積一週 |
| 未來近期 | 優先使用短期原始點資料，依每版實際時間保留逐 1／3 小時間隔 |
| 未來較遠 | 使用日夜預報，保留每筆起訖時間、平均值及高低範圍 |
| 每日預報 | 使用逐日產品，保留每筆實際起訖時間與是否涵蓋完整日 |

不把 15:30 的 GT 改寫成 15:00 的整點紀錄，也不自行插補成官方逐小時預報。短期與日夜產品銜接時，按各項資料的實際涵蓋時間選用，保留來源；不重複顯示同一項目的重疊時段，沒有有效值就留白。

### 相對時間範圍怎麼讀

選擇頁用「前幾小時」「第幾到第幾小時」標示範圍，起點是各產品這一版的預報起點，並非每次開頁時的現在。具體範圍由已核對樣本的原始時間整理，後續接上新資料時需重新計算。

短期、日夜和逐日產品各自提供資料，時間可以重疊；不是到某個時間後就一律從每小時換成每 3、12、24 小時。首段不足標準長度、紫外線僅白天有值，以及較遠降雨機率缺值，都分開標示。點資料的末端是最後一筆時間，時段資料的末端才是時段結束時間。

## 預計保存什麼

| 類別 | 預計保存的內容 |
| --- | --- |
| 最新現況 | 同鄉鎮、同資料時間的一組氣溫、體感、濕度，以及來源與取得時間 |
| 過去整點走勢 | 最近一週的氣溫、體感、濕度；保存鄉鎮、來源、官方資料時間、取得時間與品質／缺值狀態 |
| 每日紀錄高低值 | 氣溫、體感各自的最高與最低值、各自對應的資料時間與取得時間，以及涵蓋情況與待核對標記 |
| 未來預報 | 已選用項目的點資料／時段資料、地點、產品、來源版本、發布及更新時間、起訖時間、取得時間與缺值狀態 |

目前不打算永久保存全部細間隔 GT；每次取得新值仍先比較高低紀錄。每日高低紀錄、原始整包及舊版預報要保留多久，尚待決定。

## 每日最高／最低怎麼記錄

### 已取得的紀錄

1. 氣溫、體感各自保存最高與最低值。每次讀到新的有效 GT 都比較，有更高／更低就更新，並記錄該筆時間；不是每小時才比較。
2. 補回的有效整點資料若有更高／更低值，也更新所屬日期的紀錄；整點走勢仍保留官方原值。
3. 日期按官方資料時間換算為臺灣時間，歸入當天 00:00 至隔日 00:00（不含隔日 00:00）。晚收到昨天資料仍更新昨天；跨日另開一天。
4. 畫面標示 **「本系統紀錄最高／最低」**。這是我們讀到的鄉鎮 GT 高低值，不是官方直接提供的完整日極值，也不代表整個鄉鎮每個位置。
5. 今天尚未結束時紀錄會繼續變動；啟用首日、漏讀與中斷期間保留涵蓋情況。一天結束後仍稱紀錄，不改稱官方最終日高低值。

### 今天與未來的預報

- 使用整包的逐日最高／最低氣溫與體感，標示 **「預報」**，與已取得的紀錄分開保存、顯示。
- 預報首段可能不足一天。例如本次逐日首段是 **12:00～24:00**，其高低值只能代表這個時段，不能當成今天全天預報。
- 日夜產品的晚上通常跨日，不能直接把白天與晚上合併成同一日曆日的逐日結果。

## 避免重複、補漏與修訂

1. **同一筆怎麼認**：GT 與整點資料依「鄉鎮＋來源＋官方資料時間」比對，各項數值分欄保存；每日高低紀錄依鄉鎮、日期、氣象項目保存。
2. **相同就跳過**：每小時重讀近 24 小時會有大量重疊，內容相同不重複新增。
3. **缺少就補入**：晚到的整點資料補回原時間。例如 17:00 的資料在 17:20 取得，仍記在 17:00。
4. **修訂要先確認**：同一筆有不同內容時，確認是較新修訂後再更新，保存來源、資料時間、取得時間及可用的版本資訊；舊版回應不覆蓋已確認的新版本。**GT 修訂先後的辨識方法尚未完成驗證**，不能只因較晚取得就認定內容較新；無法判定時保留差異並標示待核對。
5. **高低值一起核對**：若修訂影響已保存的極值，有足夠紀錄才重算；不足時保留待核對標記，不能只持續擴大高低範圍。
6. **補不到就留白**：不以 0、測站、預報、插值或舊值冒充缺少的同來源 GT；異常或無效值不納入高低統計。
7. **預報另外管理**：依地點、產品、項目、點資料時間／時段起訖與版本更新對應預報。預報過了時間仍是預報，不直接改成實測，也不拿來補 GT 缺漏。

例如：17:00 保存一輪，18:00 再讀近 24 小時，已有且相同的紀錄跳過，只補新資料、缺漏或已確認的修訂。

## 限制與尚待決定的事

- **過去一週要累積**：剛啟用先取得近 24 小時，再逐步累積；尚未確認能直接補滿同來源的過去一週。
- **補漏有期限**：服務中斷超過官方可取得範圍時，較早缺漏可能無法補回。
- **高低值可能漏掉**：兩次讀取之間的變化、服務中斷、來源延遲或缺值，都可能漏掉極值；整點補滿不代表整個日子的高低值完整。
- **修訂可能無法完整重算**：不永久保存全部細間隔資料時，極值遭官方修正或判為無效，可能缺少足夠紀錄重算，須標示待核對。
- **測站不混用**：測站 API 的官方日高低值尚未確認能與鄉鎮 GT 對齊，因此不納入這套鄉鎮紀錄來源。
- **仍需驗證**：GT 的詳細取點、分析與發布規則、公開檔案的長期穩定性、修訂辨識流程，以及整包與查詢 API 上線是否同步。
- **仍需決定**：候選項目要加入哪些、每日高低紀錄與舊版資料保留多久，以及後端如何持續執行與保存。
