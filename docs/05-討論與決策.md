## 紀錄方式

以下按議題整理對話摘要，不是逐字稿。沒有明確說出日期的個別訊息，不另外編造時間。所有議題均來自截至 2026-11-11 的本次對話。

使用者同意「先做一版」表示授權製作範本；不等於已接受每個配色、名稱、預設地點或資料算法。

## D01 · 從一般天氣 App 收斂到時間趨勢

- 使用者最初希望利用中央氣象署資料製作 Web App，先進行討論。
- 助理提出日常助手、通勤、戶外與觀測看板等方向作為例子。
- 使用者接著指出要看溫度、體感及濕度，涵蓋前一週、後一週及今天、近幾天等範圍。
- **已確認需求**：三種核心數值、以今天為優先、能回看與展望一週。
- **未形成需求**：早期舉例的雷達、通勤、戶外評分等，不自動納入本版。

## D02 · 固定時段按鈕與無級縮放

- 助理早期先提議今天、近幾天、3 天及一週等時段切換。
- 使用者進一步澄清，希望「小時到周無級縮放」。
- **已確認需求**：同一張時間軸能連續改變範圍，不只切換幾個固定頁籤。
- **第一版方案**：保留時段按鈕作為快速定位，另加連續縮放、平移及兩週總覽。
- **待確認**：1 小時的下限、首頁是否以現在置中，以及總覽是否保留。

## D03 · 過去資料是否需要自行累積

- 使用者詢問氣象署是否已有紀錄，還是需要 App 自己額外紀錄。
- 本次查閱發現官方有最近 30 天觀測等歷史資料，可作為前一週溫度、濕度、風速的來源。
- **資料結論**：若所需測站及時段有資料，可能直接補入，不必先等 App 運作一週。
- **助理建議／第一版方案**：取得官方歷史資料，再於分頁使用期間暫存新的觀測。
- **待驗證**：實際測站涵蓋、發布延遲、下載及瀏覽器直接讀取的可行性。
- **未確認需求**：持續的背景蒐集、集中資料庫與跨裝置同步。

## D04 · 官方是否提供體感

- 使用者多次確認「有沒有體感」與「有沒有過去的體感」。
- **本次查閱結果**：短期預報有體感；一週預報有最高／最低體感。本次選用的觀測／歷史資料沒有直接列出體感欄位。
- **表述修正**：不應把上述限制寫成氣象署所有服務都不存在任何歷史體感資料。
- **助理提案／第一版方案**：使用歷史氣溫、濕度、風速估算，並標示「估算體感」。
- **待確認**：使用者是否接受估算作為正式的歷史體感呈現。
- **待驗證**：公式適用性與真實資料的一致性。

## D05 · 全前端的可行性

- 使用者詢問是否能做全前端，之後明確要求先做一版全前端。
- **已確認需求**：本階段採全前端。
- **第一版方案**：靜態 HTML／CSS／JavaScript、瀏覽器內計算與快取，由使用者輸入自己的授權碼。
- **已說明限制**：前端不能隱藏授權碼、關閉網頁不會持續紀錄、官方下載是否允許跨網站讀取要實測。
- **待驗證**：使用有效授權碼時，觀測、歷史與預報能否完整讀取。
- **尚未採用**：後端轉接服務；只有確定必要資料不能直接讀取後，才重新討論是否改方案。

## D06 · 簡約設計與流暢動畫

- 使用者要求「簡約好閱讀、操作簡單、現代簡約、文字盡可能少或用其他表達方式、過渡有動畫」。
- **已確認需求**：上述體驗與視覺目標。
- **第一版方案**：淺色背景、橘／紫／藍三色、雙圖同步、裝飾圖示、約 280 毫秒的時間軸過渡。
- **待確認**：是否喜歡目前配色、字級、資訊密度、雙圖布局及動畫幅度。
- **待驗證**：實機手勢、可讀性與連續操作的流暢度。

- 使用者明確同意依分類建立檔案，放在專案內，並要求清楚區分需求、已完成與待確認。

## D10 · GitHub Pages 與推送自動部署

- 使用者希望手機能查看網站，後續選擇「用 GitHub Pages」，並確認前端改動推送後是否能自動部署。
- **已確認需求**：採 GitHub Pages 發布；推送前端後自動部署。
- **本次方案**：`main` 上 `dist/**`、核心測試或部署流程有變更時，先檢查，再只發布 `dist/`；純文件變更不部署。另提供手動執行入口。
- GitHub Pages 入口為 `https://howiedagg.github.io/weather/`，是公開的靜態網站；不需要 ChatGPT 登入。
- **狀態區分**：部署流程寫入程式，不等於 Pages 已啟用或已成功上線。需要確認倉庫的 Pages 來源及首次執行結果。
- 現有 GitHub 工具沒有 Pages 來源設定操作；本次 Windows Firefox 自動操作因瀏覽器網址政策檢查不支援而停止。若仍未啟用，需要使用者在設定頁選擇一次 GitHub Actions。
- 不將 API 授權碼寫進 GitHub；關頁後不持續記錄的全前端限制仍然適用。

## 後續如何記錄決定

新增議題時依序編號，至少記錄：問題、使用者決定或助理提案、目前實作、未解決部分。完成實際驗證後，另記錄資料來源、日期與結果，避免把推測改寫成事實。
